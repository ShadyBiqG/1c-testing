## Автоматизированное тестирование 1С

Для любой задачи, которая изменяет наблюдаемое исполняемое поведение BSL или UI, автоматизированная проверка фактического результата является частью Definition of Done, а не speculative-доработкой.

Перед разработкой или исправлением такой функциональности загружай `.codex/skills/1c-testing/SKILL.md` и следуй его workflow.

Обязательные правила:

- до подробного исследования выбери ширину проверки L1/L2/L3/L4 и отдельно risk profile `low` / `normal` / `strict`; проведение, движения, транзакции, права/RLS и интеграции требуют строгой целевой проверки, но сами по себе не делают локальную правку L1;
- дымовая runtime-проверка обязательна на каждом уровне; для UI сначала используй OneRPA QA MCP/TestClient: открыть затронутую форму, проверить ожидаемое состояние/действие и `ui_errors`, затем закрыть; для L4 не создавай `.feature` только ради формального smoke, если QA MCP даёт достаточное подтверждение;
- полный уровень относится к затронутой функциональности, а не автоматически ко всей конфигурации; не повторяй успешный неизменённый набор без новой причины;

- по умолчанию используй YAxUnit для серверной бизнес-логики и BSL; для проведения/движений и взаимодействия нескольких модулей предпочитай integration-тест с реальными объектами;
- OneRPA QA MCP/TestClient используй для быстрого developer smoke и проверки изменённого UI;
- Vanessa используй для долговечных UI regression, acceptance и end-to-end сценариев;
- отсутствие проверки, требуемой выбранным уровнем и risk profile, означает, что нужно создать минимальное полезное покрытие; не создавай новый unit/Vanessa-тест только ради ритуала, если контракт надёжно закрывается существующим тестом или QA smoke;
- тесты YAxUnit храни в тестовом расширении проекта и группируй по функциональным блокам;
- переиспользуй существующий тестовый модуль; не создавай отдельный общий модуль на каждую задачу;
- используй минимальную воспроизводимую основу стенда; данные сценария создавай через переиспользуемые модули-помощники по подсистемам/операциям согласно `references/test-data.md` скилла; фиксированное количество модулей не требуется;
- не выдумывай имя тестового модуля: перед запуском проверь реальный каталог/метаданные тестового общего модуля;
- при наличии доступного MCP `v8_runner` сборку и тесты выполняй через него, CLI `v8-runner.exe` используй как fallback;
- основной узкий вызов через MCP — `run_module_tests` с реальным `moduleName`; он сам выполняет build prerequisite;
- полный YAxUnit-прогон через MCP — `run_all_tests` с `runner = yaxunit`;
- Vanessa через MCP — `run_all_tests` с `runner = vanessa`;
- основной цикл Vanessa — проверка файла и полный запуск целевого сценария через `v8_runner`; PASS подтверждается его отчётом;
- Vanessa MCP используй только точечно после доказанного падения для поиска неизвестного шага, неоднозначного синтаксиса или инспекции конкретного элемента формы;
- не запускай весь сценарий и не подтверждай PASS пошаговым выполнением в Vanessa MCP или в уже изменённом состоянии TestClient;
- до WORK сообщай режим окружения (`full`, `yaxunit_only`, `limited`); отсутствие обязательного уровня тестирования требует явного согласия пользователя на ограниченную проверку;
- не дублируй один и тот же прогон через MCP и CLI без диагностической причины;
- CLI обязателен только для операций, которых нет в MCP, например `v8-runner.exe extensions --name <SourceSet>`, а также для намеренного `--no-build` или недоступного MCP;
- `--no-build` не является стандартным режимом разработки и используется только для специально подготовленной базы;
- при исправлении дефекта следуй выбранному уровню: для L1–L3 по возможности сначала воспроизведи дефект тестом; для L4 достаточно исправления и smoke;
- не откатывай и не удаляй чужие незакоммиченные изменения ради воспроизведения RED;
- любой неуспех сначала классифицируй как `PRODUCT`, `TEST`, `INFRASTRUCTURE` или `REQUIREMENT`; `junit_empty`/`0 сценариев`, build/startup/MCP timeout относятся к инфраструктуре/обнаружению и не являются `PRODUCT` FAIL;
- создание/изменение метаданных тестового расширения подчиняется `1c-metadata-manage` из `ai_rules_1c`.

Исключение из обязательного теста допустимо для комментариев/форматирования/документации либо когда автоматическая проверка объективно недоступна; причину нужно явно сообщить.

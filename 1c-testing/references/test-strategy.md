# Runtime test strategy

## Цель

Выбрать минимальный набор проверок, который действительно доказывает изменённый контракт 1С. Ширина проверки и риск — разные оси:

- **breadth L1–L4** — сколько затронутого поведения проверяем;
- **risk profile low/normal/strict** — какие проверки нельзя пропустить.

Строгий риск не означает полный регресс автоматически.

## Матрица runtime-слоёв

| Изменение / контракт | Основная проверка | Дополнение |
|---|---|---|
| Чистая серверная BSL-логика, расчёт, преобразование | YAxUnit unit/contract | targeted module run |
| Запрос на контролируемых данных | YAxUnit | при необходимости read-only live-IB для фактической выборки |
| Проведение документа, движения, регистры | YAxUnit integration | реальные объекты; проверить нужные движения/состояния |
| Взаимодействие нескольких серверных модулей | YAxUnit integration | проверить сквозной результат, а не внутренние вызовы |
| Форма, клиентский код, команда | OneRPA QA MCP/TestClient | open → action → assert → ui_errors |
| Долговечный UI regression | Vanessa Automation | воспроизводимый `.feature` через v8-runner |
| Сквозной бизнес-процесс пользователя | Vanessa Automation | E2E только для действительно связанного пользовательского пути |
| Права, RLS, current user | runtime под business user | технический full-rights user недостаточен |
| Интеграция / background job | integration/job test | проверить внешне наблюдаемый результат; не ходить в production endpoint |
| Metadata-only без самостоятельного поведения | build/check + применимый smoke | отдельный бизнес-тест только если меняется runtime-контракт |

## Coverage matrix для сложной задачи

Перед реализацией достаточно короткой таблицы:

| Requirement | Runtime layer | Test type | Target | User/context | Expected result |
|---|---|---|---|---|---|
| R1 | server | YAxUnit integration | тестовый модуль X | technical test user | движения Y |
| R2 | UI | QA MCP + existing Vanessa | форма Z | business user | команда доступна, результат виден |

Каждый обязательный requirement должен иметь хотя бы один наблюдаемый expected result. Один test может покрывать несколько requirements, если он явно доказывает каждый из них.

## Breadth L1–L4

- **L4** — один локальный контракт; один достаточный smoke/runtime-check.
- **L3** — адресное изменение поведения; smoke + targeted behaviour test.
- **L2** — несколько связанных контрактов/методов; все изменённые контракты и ближайшее влияние.
- **L1** — новая крупная функциональность, широкое/неограниченное влияние или много затронутых контрактов.

Не повышай breadth только из-за того, что изменение находится в проведении/RLS/интеграции. Для этого существует risk profile.

## Risk profile

### low

Локальная логика без существенных side effects. Достаточны проверки выбранного breadth.

### normal

Обычное бизнес-правило, запрос, форма или несколько связанных методов. Добавь targeted behaviour check и затронутый regression.

### strict

- проведение/движения;
- транзакции/блокировки;
- права/RLS/current user;
- публичный контракт;
- интеграция/background job;
- общий механизм нескольких подсистем.

Для `strict` обязателен релевантный integration/runtime check. Локальный strict-change обычно получает минимум L3; L1 нужен только при широком или неизвестном влиянии. L4 оставляй для изменений без нового/изменённого бизнес-контракта.

## UI: QA MCP или Vanessa

Используй **QA MCP/TestClient**, когда нужно быстро доказать текущую правку:

- форма открывается;
- нужный элемент существует/доступен;
- изменённое действие выполняется;
- ожидаемое состояние видно;
- нет `ui_errors`.

Используй **Vanessa**, когда сценарий должен жить в Git и регулярно повторяться как regression/acceptance/E2E, либо такой сценарий уже существует.

Не создавай Vanessa `.feature` для каждой маленькой UI-правки.

## Пользовательский контекст

Если результат зависит от пользователя/ролей:

1. Определи business user или набор ролей.
2. Подготовку данных можно сделать техническим пользователем.
3. Проверяемое бизнес-действие выполняй под business user.
4. Не выдавай ему технические роли ради теста.
5. Не сохраняй реальные секреты в тестовом коде/feature.

Если YAxUnit не может воспроизвести нужный user context, перенеси этот requirement в integration/UI runtime layer.

## Классификация результата

### PRODUCT

Тест действительно выполнялся и доказал неверное production behavior. Можно исправлять production-код.

### TEST

Ошибка теста, fixture, подготовки данных, assertion, локатора или шага. Исправляй тест/фикстуру/шаг, не production.

### INFRASTRUCTURE

Build/startup/MCP/transport/timeout, `junit_empty`, `0 сценариев`, неверный filter/module, неактивное расширение, недоступная тестовая ИБ. Production-код на основании этого сигнала не меняй.

### REQUIREMENT

Нельзя однозначно установить правильный expected result либо тест и спецификация конфликтуют. Останови зависимое изменение и уточни контракт.

## Финальный verification floor

На финальном состоянии:

1. touched BSL проходит обязательные validation gates `ai_rules_1c`;
2. source/runtime соответствует тестовой ИБ через v8-runner build/check;
3. серверный изменённый контракт проходит targeted YAxUnit;
4. UI-контракт проходит QA MCP/TestClient;
5. сохраняемый E2E/regression проходит Vanessa, если он применим;
6. strict-risk контракт имеет соответствующую integration/runtime проверку.

Worker/reviewer report не заменяет эти доказательства.

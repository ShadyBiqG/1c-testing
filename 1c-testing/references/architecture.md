# Архитектура тестов

## Цель

Архитектура должна позволять быстро находить тесты к изменяемому коду, не плодить модуль на каждую задачу, группировать тесты по функциональным блокам и отделять фабрики данных от тестов поведения.

## Три слоя runtime-проверки

Архитектура тестов не означает «каждая правка должна иметь YAxUnit и Vanessa одновременно».

- **YAxUnit** — серверная бизнес-логика и integration через реальные объекты БД.
- **OneRPA QA MCP/TestClient** — быстрый developer smoke и проверка изменённого UI без обязательного появления нового файла теста.
- **Vanessa Automation** — сохраняемые UI regression, acceptance и end-to-end сценарии.

Выбор слоя следует [test-strategy.md](test-strategy.md). Для L4 UI-fix QA smoke достаточен, если долговечный regression не требуется.

## Физическая структура

```text
tests/
└── src/
    ├── Configuration/
    └── CommonModules/
        ├── ТестДанные_НСИ/
        ├── ТестДанные_Документы/
        ├── Тест_Склад_Док_ПеремещениеТоваров_МО/
        ├── Тест_ВЕТИС_ОМ_ГашениеВходящихВСД/
        └── ...
```

Если фактический source-set устроен иначе, следуй `v8project.yaml` и существующей структуре. Не перемещай дерево тестов только ради этого документа.

## Организация помощников данных

Группируй повторяемую подготовку по подсистемам, объектам или связным операциям,
а не по номерам задач. Один помощник может подготовить несколько связанных
документов и вернуть их ссылки, используя переиспользуемые фабрики объектов.
Количество модулей выбирай по размеру проекта; не создавай заранее пять пустых
модулей. Минимальная основа стенда и данные сценария имеют разное время жизни.
Подробный контракт: [test-data.md](test-data.md).

## Функциональные блоки

Сначала переиспользуй блоки проекта. При отсутствии словаря используй: `НСИ`, `Продажи`, `Закупки`, `Склад`, `Доставка`, `ВЕТИС`, `Ценообразование`, `Обмены`, `Финансы`, `Печать`, `Интеграции`, `РегламентныеОперации`, `Общее`.

Новый блок создавай только когда ни один существующий не описывает владельца поведения.

## Имена тестовых модулей

Формат: `Тест_<Блок>_<ТипОбъекта>_<ИмяОбъекта>[_<ТипМодуля>]`.

Префиксы: `ОМ`, `Спр`, `Док`, `РН`, `РС`, `РБ`, `РР`, `Обр`, `Отч`, `БП`, `ПО`, `Пер`, `Зад`, `ПС`, `ПВХ`, `ПВР`.

Суффиксы: `_МО` — модуль объекта; `_ММ` — модуль менеджера; `_НЗ` — модуль набора записей; без суффикса — общий модуль/функциональность без отдельного контекста.

Примеры:

```text
Тест_Склад_Док_ПеремещениеТоваров_МО
Тест_Склад_Док_РасходныйОрдерНаТовары_МО
Тест_НСИ_Спр_Номенклатура_ММ
Тест_ВЕТИС_ОМ_ГашениеВходящихВСД
Тест_Доставка_Док_ПутевойЛист_МО
Тест_Ценообразование_ОМ_РасчетЦен
```

## Имена тестовых методов

Описывай поведение: `ВесРассчитываетсяПоУпаковкам`, `ПриПустойСерииНеВозникаетОшибка`, `ПриНедостаточномОстаткеВозвращаетсяОтказ`.

Для регрессии с известным номером задачи: `ЕР12854_ВесРассчитываетсяПоУпаковкам`. Не выдумывай номер.

## Наборы внутри модуля

Один общий модуль может содержать несколько наборов YAxUnit, например `Расчет веса`, `Проверка остатков`, `Заполнение упаковок`, `Регрессии`. Это предпочтительнее отдельных общих модулей для каждого маленького кейса.

## Когда создавать новый модуль

Создавай при новом объекте-владельце, семантически чужой функциональности или отдельном типе модуля, когда это улучшает локальный прогон.

Не создавай новый модуль только потому, что пришла новая задача/тикет или добавился один тест.

## Сквозная регрессия

`Тест_Регрессия_<НомерЗадачи>` допустим только когда изменение охватывает несколько независимых владельцев и тест невозможно разумно поместить в один функциональный модуль.

## Vanessa

`.feature` не размещай внутрь source-set YAxUnit-расширения, если его корень загружается Конфигуратором как дерево метаданных.

Безопасная структура:

```text
features/
├── 00_Подготовка/
├── 10_НСИ/
├── 20_Продажи/
├── 30_Закупки/
├── 40_Склад/
├── 50_ВЕТИС/
├── 60_Доставка/
├── 70_Интеграции/
└── 80_EndToEnd/
```

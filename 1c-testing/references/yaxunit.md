# YAxUnit — правила написания тестов

## Обнаружение тестов

YAxUnit обнаруживает тесты через экспортную процедуру:

```bsl
Процедура ИсполняемыеСценарии() Экспорт
```

В ней тесты регистрируются через `ЮТТесты`. Не используй устаревшую сигнатуру с параметром.

Тесты располагаются в общих модулях тестового расширения. Модуль не должен быть `Глобальный` или `ВызовСервера`; контекст клиента/сервера должен соответствовать тестируемому коду.

## Регистрация

```bsl
Процедура ИсполняемыеСценарии() Экспорт

	ЮТТесты
		.ДобавитьТестовыйНабор("Расчет веса")
			.ДобавитьТест("ВесРассчитываетсяПоУпаковкам")
			.ДобавитьТест("ПриПустойУпаковкеВесНеИскажается");

КонецПроцедуры
```

Имя в `ДобавитьТест()` должно соответствовать экспортной тестовой процедуре.

## Arrange → Act → Assert

Каждый тест логически делится на подготовку, одно основное действие и проверки наблюдаемого результата.

Основной assertion:

```bsl
ЮТест.ОжидаетЧто(ФактическоеЗначение).Равно(ОжидаемоеЗначение);
```

Доступны, в частности: `Равно`, `НеРавно`, `Больше`, `БольшеИлиРавно`, `Меньше`, `МеньшеИлиРавно`, `Заполнено`, `НеЗаполнено`, `ЭтоИстина`, `ЭтоЛожь`, `ЭтоНеопределено`, `ЭтоNull`, `ИмеетТип`, `ИмеетДлину`, `Содержит`, `НеСодержит`, `Свойство`.

Для проверки состояния базы используй специализированные утверждения YAxUnit, например `ЮТест.ОжидаетЧтоТаблицаБазы`, когда это устойчивее ручного запроса.

Перед редким методом API сверяйся с версией YAxUnit проекта.

## Unit/contract и integration

Не выбирай вид YAxUnit-теста по названию задачи. Выбирай по наблюдаемому контракту.

### Unit/contract

Подходит для локального бизнес-правила, расчёта/преобразования, функции с контролируемыми входами и запроса на подготовленных данных. Изолируй только внешние зависимости, которые не являются частью проверяемого поведения. Не мокай сам проверяемый бизнес-контракт.

### Integration

Обязателен как минимум для строгой проверки, когда меняются проведение документа, движения/регистры, взаимодействие нескольких серверных модулей, цепочка «создание → запись/проведение → движения/остатки/состояние» или иные side effects в БД, являющиеся частью требования.

Integration-тест использует реальные объекты и данные тестовой ИБ. Проведение и движения не подменяются моками. Если проверяется документ, утверждения должны подтверждать нужные движения/состояния, а не только успешное завершение вызова.

Ожидаемый результат получай независимо от production-алгоритма: из требования, входной fixture или заранее рассчитанного набора. Не вызывай проверяемую функцию второй раз для вычисления expected.

### Пользователь и права

Если серверный результат зависит от текущего пользователя, ролей, RLS или привилегированного режима, явно укажи требуемый user/role context. Прогон YAxUnit под техническим full-rights пользователем не доказывает поведение обычного пользователя. Если YAxUnit не может воспроизвести нужный контекст, перенеси этот контракт в runtime/integration/UI-проверку и зафиксируй ограничение.

## Параметризованные тесты

```bsl
ЮТТесты
	.ДобавитьТест("КоличествоКоробок")
		.СПараметрами(10, 5, 2)
		.СПараметрами(0, 5, 0);
```

Процедура теста принимает параметры в том же порядке.

## Независимость

Тесты не зависят от порядка запуска, не используют данные другого теста, не ожидают заранее существующие коды/номера без необходимости и не оставляют критичное состояние для следующего теста.

## Метаданные

Если общий модуль отсутствует и проект использует `ai_rules_1c`, создание/регистрацию метаданных проводи через `1c-metadata-manage`, а не ручной правкой XML.

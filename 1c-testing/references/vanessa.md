# Vanessa Automation: проектирование, написание и проверка сценариев

## Роль Vanessa

Vanessa проверяет наблюдаемое поведение пользователя: формы, навигацию, команды,
права, взаимодействие окон и критические end-to-end цепочки. Она не должна
дублировать варианты бизнес-логики, которые дешевле и точнее покрываются YAxUnit.

Если изменение затрагивает и бизнес-правило, и UI, используй два слоя:

- YAxUnit подтверждает расчёты, движения, запросы и ошибки бизнес-логики;
- Vanessa подтверждает, что пользователь может выполнить критический путь и видит
  ожидаемый результат.

## Что прочитать до написания `.feature`

1. Требование и `test-plan`: для каждого сценария должна быть понятна проверяемая
   бизнес-ценность и ожидаемый наблюдаемый результат.
2. `v8project.yaml`: реальные профиль Vanessa, каталог feature, теги и способ запуска.
3. Ближайшие `.feature` проекта и проектную библиотеку шагов: их соглашения имеют
   приоритет перед универсальными примерами этого skill.
4. Метаданные и код затронутой формы: технические имена элементов, команды,
   заголовки и навигационные точки нельзя угадывать.
5. Доступность Vanessa MCP как дополнительного диагностического канала. Его отсутствие
   не блокирует работу, если сценарий можно проверить и запустить через `v8_runner`.

Не начинай генерацию с общего шаблона, пока не найден аналог проекта и не определён
способ подготовки данных.

## Контракт хорошего сценария

Каждый сценарий должен иметь один проверяемый смысл:

1. **Дано** — минимальное состояние, необходимое именно этому сценарию.
2. **Когда** — одно ключевое пользовательское действие или короткая цельная операция.
3. **Тогда** — наблюдаемый результат из требования.

Сценарий не считается тестом, если он только открывает форму, нажимает кнопки или
проверяет отсутствие технического исключения. Нужна содержательная проверка:
значение, состояние, доступность, сообщение, созданный объект или видимый результат
бизнес-операции.

Перед записью шагов составь короткую карту:

| Требование | Предусловие | Действие | Проверяемый результат |
|---|---|---|---|
| `<что должно работать>` | `<какие данные нужны>` | `<что делает пользователь>` | `<что он видит>` |

Если в колонке результата нет конкретной проверки, сценарий ещё не спроектирован.

## Границы и размер

- Один сценарий — одна причина падения и одна бизнес-цель.
- Не объединяй создание данных, несколько независимых операций и проверку отчёта в
  один «полный цикл», если части можно диагностировать отдельно.
- Повторяющуюся бизнес-подготовку выноси в существующий экспортный сценарий или
  проектный шаг только после поиска уже имеющейся реализации.
- Не вводи собственный шаг ради сокрытия одного-двух стандартных действий. Новый
  шаг оправдан для устойчивой доменной операции, повторяющейся в нескольких feature.
- Длинный сценарий разбивай по бизнес-результатам, а не по произвольному числу строк.
  Более 35 исполняемых шагов требует явного обоснования на ревью.

## Поиск и выбор шагов

Формулировка шага — это API. Не пиши шаг из памяти и не исправляй неизвестный шаг
«на глаз».

Основной путь поиска — существующие feature проекта и локальный каталог шагов. Он
быстрее и не зависит от состояния запущенного TestClient:

```powershell
python .\vendor\va-ai\tools\search-steps\search_steps.py `
  --query "ожидание появления элемента" "значение поля с именем" `
  --top 10 --format human

python .\vendor\va-ai\tools\validator\validate.py `
  "<путь-к-сценарию.feature>" --compact
```

Vanessa MCP подключай точечно, когда статического поиска недостаточно:

1. Неизвестный шаг — один поиск через `search_for_steps_by_keywords`.
2. Не найден элемент формы — один снимок текущего состояния доступным read-only tool.
3. Синтаксическая неоднозначность — `check_syntax` для сохранённого файла.

Не выполняй весь сценарий через Vanessa MCP по умолчанию. Не используй пошаговое
выполнение для доказательства PASS: оно наследует состояние клиента и не воспроизводит
чистый запуск. После любой MCP-диагностики исправь файл и снова запусти целевой
сценарий целиком через `v8_runner`.

Локальная библиотека — снимок известной версии Vanessa, а не доказательство наличия
шага в запущенной обработке. При появлении MCP повтори поиск и синтаксическую
проверку на фактической версии.

Файлы `vendor/va-ai/ai-knowledge/guide.md` и `templates.md` — справочный материал
для поиска возможностей, но **не стандарт архитектуры тестов**. Не копируй из них
без проверки фиксированные ссылки, абсолютные пути, паузы, тестовые значения и
длинные демонстрационные сценарии.

## Устойчивые локаторы

Предпочтение при обращении к элементу формы:

1. техническое имя элемента (`... с именем ...`), подтверждённое метаданными,
   кодом формы или состоянием тестового клиента;
2. устойчивый пользовательский заголовок, если техническое имя недоступно;
3. позиция или номер строки — только когда это часть требования и набор данных
   полностью создан самим сценарием.

Не угадывай имя элемента по синониму реквизита. Не смешивай в одном сценарии
техническое имя и разные варианты заголовка одного элемента без причины.

Избегай координат, порядка строк, активной строки «по умолчанию», случайного первого
элемента списка и заголовков окон с динамическими значениями. Если проект уже
использует устойчивый доменный шаг для выбора объекта, переиспользуй его.

## Тестовые данные и независимость

Сценарий должен проходить отдельно, повторно и в составе suite.

- Создавай минимальные данные через существующие сценарии подготовки, API или
  утверждённый эталон проекта.
- Используй уникальный признак запуска по принятому в проекте механизму. Не изобретай
  синтаксис переменных Vanessa: сначала найди пример проекта или реальный шаг.
- Не полагайся на объект «Основной склад», «Товар 1» или пользователя, если их
  наличие не гарантировано эталоном и не оформлено как инвариант окружения.
- Не вставляй `e1cib/data/...?...ref=<фиксированная ссылка>`: ссылка из другой базы
  или после восстановления данных неустойчива. Создай/найди объект по бизнес-ключу
  и сохрани полученную ссылку штатным шагом проекта.
- Не используй абсолютные локальные пути. Тестовые файлы размещай в репозитории или
  получай путь из настройки/переменной окружения, принятой проектом.
- Очистка не должна удалять чужие данные. Удаляй только объекты текущего сценария
  либо восстанавливай изолированную тестовую базу штатным процессом.
- Сценарии не должны зависеть от порядка запуска друг друга. Общую подготовку
  объявляй явно, а не через надежду, что раньше уже прошёл другой feature.

`Контекст` и секция `Переменные` допустимы только если они уже приняты в проекте и
поддерживаются его версией/профилем Vanessa. Не добавляй их автоматически: разные
проекты сознательно используют разные соглашения.

## Ожидания и асинхронность

Не лечи нестабильность фиксированной паузой. После действия, которое обновляет форму
или выполняется асинхронно, найди стандартный шаг ожидания конкретного состояния:
появления/исчезновения элемента, открытия/закрытия окна, завершения фоновой операции.

`Пауза` допустима только как временная диагностика или для внешней системы без
наблюдаемого признака готовности. В постоянном тесте она требует комментария с
причиной и ограниченного времени; предпочтительно заменить её ожиданием условия.

После критического действия сначала дождись состояния, затем проверь бизнес-результат.
Само ожидание не является утверждением о корректности результата.

## Ошибки, модальные окна и права

- Перед сценарием закрой только окна, которые мешают изоляции, принятым шагом проекта.
- Ожидаемое предупреждение проверяй по устойчивой смысловой части текста, если полный
  текст содержит дату, номер или другое динамическое значение.
- Не закрывай неожиданное предупреждение и не продолжай сценарий: это должна быть
  ошибка теста с evidence.
- Сценарий прав выполняй под явно выбранным профилем пользователя. Не считай текущий
  случайный TestClient доказательством требуемой роли.
- Негативный сценарий подтверждает и сообщение пользователю, и отсутствие запрещённого
  результата (например, объект не записан или команда недоступна).

## Теги и размещение

Сохраняй существующую структуру проекта. Если её нет, допустима структура по
функциональным блокам:

```text
features/
└── 40_Склад/
    └── 01_ПеремещениеТоваров/
        ├── 01_Создание.feature
        └── 02_Проведение.feature
```

Используй только реально принятые теги. `@Draft`, `@Ignore...` и исключение из CI не
являются способом «сдать» незавершённый тест. Если сценарий обязан входить в gate,
проверь, что фильтры профиля действительно его выбирают.

## Основной цикл: v8-runner first

1. Зафиксируй карту `требование → действие → проверка`.
2. Найди ближайший feature и способ подготовки данных.
3. Подтверди технические имена элементов и команды.
4. Найди формулировки шагов в feature проекта и offline-каталоге; Vanessa MCP
   используй только для оставшейся неоднозначности.
5. Напиши минимальный сценарий с явным результатом.
6. Выполни offline validator. `check_syntax` Vanessa MCP вызывай только если локальная
   проверка дала неоднозначный результат или фактическая версия Vanessa отличается.
7. Из каталога этого skill выполни quality-check:

   ```powershell
   python .\scripts\check_vanessa_quality.py "<путь-к-feature>"
   ```

8. Сразу запусти один целевой feature/сценарий через `v8_runner`, используя реальные
   `feature` или `scenarioFilter` из live schema и конфигурации проекта.
9. При FAIL сначала прочитай JUnit, `runner.log` и остальные указанные артефакты.
   Классифицируй причину: шаг не найден, элемент не найден, business assertion,
   подготовка данных, запуск TestClient или инфраструктура.
10. Используй Vanessa MCP только для одного конкретного вопроса, на который не
    ответили отчёт, код формы и метаданные. Если вызов не дал нового evidence, не
    повторяй интерактивный цикл с другими догадками.
11. Исправь файл и повтори целевой сценарий целиком через `v8_runner`. Не продолжай
    выполнение с середины в изменённом состоянии клиента.
12. После локального PASS выполни требуемый профильный/регрессионный прогон и прочитай
    отчёт/JUnit: загрузка feature и код возврата процесса сами по себе не PASS.

## Воспроизводимый запуск

Если MCP `v8_runner` доступен и Vanessa настроена в `v8project.yaml`, используй
`run_all_tests` с `runner = "vanessa"`. Параметры `profile`, `feature`, `filterTag`,
`ignoreTag`, `scenarioFilter` передавай только после чтения реальной конфигурации.

Для итераций, в которых менялся только `.feature`, допустим намеренный запуск без
повторной сборки уже подготовленной базы. Используй его лишь после успешной сборки
текущего состояния и только если live schema/CLI установленной версии поддерживает
нужный фильтр. Финальный gate выполняй обычным воспроизводимым запуском с build.

CLI fallback:

```powershell
v8-runner.exe test va
```

`--no-build` применяй только к специально подготовленной базе, не как стандартный
режим. Перед редкой CLI-опцией проверь `v8-runner.exe test --help` установленной
версии.

## Ревью перед PASS

Автор сценария обязан ответить «да» на все пункты:

- сценарий связан с конкретным требованием или регрессией;
- есть содержательная проверка бизнес-результата;
- каждый шаг найден в существующих feature, фактической Vanessa или закреплённом каталоге;
- имена элементов подтверждены, а не угаданы;
- данные создаются явно или гарантированы документированным эталоном;
- нет фиксированных `ref`, абсолютных локальных путей и зависимости от порядка suite;
- фиксированные паузы отсутствуют либо обоснованы и не заменяют проверку;
- неожиданное модальное окно приводит к FAIL;
- сценарий выбран фильтрами нужного профиля и реально выполнен;
- PASS подтверждён отчётом с ненулевым числом выполненных сценариев.
- финальный PASS получен полным запуском сценария через `v8_runner`, а не пошаговым
  выполнением в Vanessa MCP.

Если какой-либо пункт не выполнен, результат — не PASS. Синтаксически валидный
`.feature` ещё не является качественным тестом.

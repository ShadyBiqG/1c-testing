# Тестовые данные

## Разделение ответственности

Фабрики данных отделены от тестовых модулей.

Рекомендуемые общие модули:

```text
ТестДанные_НСИ
ТестДанные_Документы
ТестДанные_Регистры
ТестДанные_Окружение
```

Они не являются тестами и не содержат `ИсполняемыеСценарии()`.

## ТестДанные_НСИ

Назначение: организации, подразделения, склады, партнёры/контрагенты, номенклатура, упаковки, виды цен, транспорт и прочая НСИ.

Пример интерфейса:

```bsl
Функция СоздатьНоменклатуру(Параметры = Неопределено) Экспорт
	// Возвращает созданный тестовый объект или ссылку.
КонецФункции
```

## ТестДанные_Документы

Назначение: заказы, приобретения, перемещения, расходные ордера, реализации, путевые листы, доверенности и иные документы.

Фабрика документа принимает ссылки на НСИ, а не создаёт скрыто десятки несвязанных объектов без необходимости.

## ТестДанные_Регистры

Прямое создание записей регистров используй только когда тестируемый контракт действительно начинается с заданного состояния регистра либо создание состояния через публичные документы слишком тяжёлое и не относится к проверяемому поведению.

Не подменяй реальную бизнес-цепочку прямой записью регистра в интеграционном тесте проведения.

## API YAxUnit

По возможности используй `ЮТест.Данные()`.

```bsl
Номенклатура = ЮТест.Данные()
	.КонструкторОбъекта("Справочник.Номенклатура")
	.ФикцияОбязательныхПолей()
	.Установить("Наименование", "Тестовая номенклатура")
	.Записать();
```

Для реквизитов, конкретное значение которых не важно для сценария, предпочитай `Фикция(...)`, `ФикцияРеквизитов(...)`, `ФикцияОбязательныхПолей()`.

Это устойчивее, чем поиск заранее существующей записи по коду.

## Детерминизм

Плохо: искать «Основную организацию», «Оптовый склад», товар `00001`, если именно эти записи не являются частью требования.

Хорошо: создать минимальную организацию, склад, номенклатуру и передать полученные ссылки в фабрику документа.

## Очистка

Предпочитай механизмы YAxUnit для удаления созданных тестовых данных/транзакционного выполнения, когда они подходят сценарию. Ручная очистка нужна только там, где движок не может корректно обслужить данные автоматически.

Очистка не должна скрывать исходную ошибку теста.

## Повторное использование

Перед новой фабрикой найди существующий метод в `ТестДанные_*`. Если он почти подходит — расширь его параметрами без изменения существующего поведения.

Не создавай `СоздатьНоменклатуру2` или `СоздатьНоменклатуруДляТеста123` без архитектурной причины.

Фабрика создаёт данные. Проверка бизнес-правил остаётся в тестовом модуле.

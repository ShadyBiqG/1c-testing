# 1C Testing — YAxUnit + v8-runner MCP + Vanessa

## Назначение

Этот skill задаёт единый тестовый workflow для разработки 1С и дополняет `ai_rules_1c`, а не заменяет его.

- правила разработки BSL, MCP-first, изменение метаданных и проверки берутся из `AGENTS.md` и соответствующих skills `ai_rules_1c`;
- этот skill владеет архитектурой автоматизированных тестов, выбором уровня теста и циклом `изменение → build → test → анализ → исправление → повторный test`;
- `v8-runner` является оркестратором сборки/тестирования;
- Vanessa MCP — необязательный точечный диагностический инструмент; основной цикл написания, запуска и повторной проверки `.feature` идёт через `v8-runner`;
- если Vanessa MCP недоступен, используй встроенный offline-каталог `vendor/va-ai`: ищи реальные шаги и валидируй `.feature` локально, не формулируй шаги из памяти;
- если MCP-сервер `v8_runner` доступен в текущей сессии, используй его первым;
- CLI `v8-runner.exe` — fallback для операций, которых нет в MCP, либо когда MCP недоступен;
- при создании или изменении метаданных тестового расширения не редактируй XML вручную, если установлен `1c-metadata-manage`: используй его правила и инструменты.

## Обязательное правило

Для задачи, меняющей наблюдаемое исполняемое поведение BSL, тест является частью результата задачи.

Исключения: только комментарии/форматирование/документация; изменение объективно нельзя проверить автоматическим тестом на доступном уровне; пользователь прямо запретил добавлять или менять тесты.

Не создавай тест «для галочки». Тест должен проверять требование или воспроизводить регрессию.

Отсутствие подходящего теста не является причиной пропустить тестирование: создай или расширь тест на уровне, требуемом изменением. Недоступное окружение — отдельное ограничение, которое нужно обнаружить до WORK и явно согласовать с пользователем; оно не превращает `not_run` в PASS.

## Четыре уровня объёма проверки

До подробного исследования выбери уровень по diff и риску. Считай уникальные
добавленные, изменённые и удалённые процедуры/функции прикладного кода с изменением
поведения; комментарии, форматирование, тесты и помощники тестовых данных в счёт
не входят. Несколько правок одной процедуры считаются один раз.

| Уровень | Когда применять | Обязательное покрытие |
|---|---|---|
| **L1 — полный** | Новая обработка/функциональность с нуля; от 6 процедур; более 2 прикладных модулей; существенный риск | Дымовой тест, все критерии приёмки новой/изменённой функциональности, существенные границы и ошибки, регрессия затронутых зависимостей; UI/E2E для пользовательского пути |
| **L2 — сокращённый** | 3–5 процедур в 1–2 модулях; либо 1–2 процедуры в 2 модулях, без существенного риска | Дымовой тест, проверки всех изменённых контрактов и ближайших вызывающих методов, существенная граница/ошибка; только затронутые модули |
| **L3 — адресный** | 1–2 процедуры в одном модуле: меняется бизнес-правило, добавляется ветка/проверка либо smoke не покрывает изменённое поведение; без существенного риска | Дымовой тест и адресная проверка изменённого поведения; один сценарий может закрывать оба требования |
| **L4 — дымовой** | Небольшая локальная правка в 1–2 процедурах одного модуля; сохраняет контракт, без существенного риска; smoke проходит через изменённый участок | Только один дымовой тест с проверкой результата. Отдельный регрессионный тест и широкий прогон не нужны |

Для 1–2 процедур сначала проверь условия L4; если они не выполнены, выбирай L3.
Количество процедур — ориентир объёма; существенный риск имеет приоритет.

Изменение проведения/движений, транзакций, прав/RLS, публичного контракта или общего
механизма нескольких подсистем повышает уровень до L1 даже для одной процедуры.
Считай риск прикладного поведения; новый экспортный помощник тестовых данных сам
по себе не требует регрессии всей конфигурации. При неизвестном влиянии сначала
сделай адресную проверку зависимостей; если границы установить нельзя, выбери L1.
Не снижай уровень за счёт дробления одной задачи на несколько маленьких правок.

L1 означает полноту проверки затронутой функциональности, а не автоматический
прогон всей ИБ. Весь набор запускай при доказанном влиянии на него, требовании
проекта или пользователя. Число тестов следует из проверяемых контрактов, а не
из правила «одна процедура — один тест» или искусственной квоты.

Для написания теста уже существующей функции выбирай уровень по добавляемому
покрытию и риску; новый файл теста не означает разработку функциональности с нуля.
Для одних комментариев/документации/форматирования runtime-прогон не требуется.

**Дымовой тест обязателен на L1/L2/L3/L4.** Это короткий реальный запуск основной
затронутой операции с проверкой бизнес-результата. Если точка входа — форма,
подтверди открытие актуальной формы/EPF и минимальный пользовательский путь;
для серверного API достаточно серверного вызова. Только build, открытие окна
или отсутствие исключения не заменяют проверку результата. Используй уже
существующий подходящий smoke; если его нет — создай минимальный. При недоступном
запуске укажи NOT_RUN и причину, не объявляй обязательный smoke пройденным.

Сообщи одной строкой: уровень, число процедур/модулей, риск, выбранный smoke и
целевой набор. Для L3/L4 достаточно короткого плана в сообщении; отдельный документ
и независимый агент для обычной правки не нужны. Режим окружения
full/yaxunit_only/limited и проектный VERIFICATION_DEPTH — отдельные параметры.

## Экономия контекста и прогонов

- Начинай с diff, изменённых процедур, их ближайших зависимостей и готовых тестов.
  Читай только нужные разделы references; не исследуй всю подсистему для L3/L4.
- Переиспользуй подтверждённые API, фикстуры и результаты проверок, пока не изменены
  относящиеся к ним исходники, версия платформы, профиль или входные данные.
  Текущее наличие/пригодность данных проверяется подготовкой теста.
- В плане данных перечисляй новые/изменённые зависимости; для неизменных достаточно
  ссылки на проверенный контракт помощника. Не проектируй подготовку заново.
- Используй минимальный поддержанный фильтр запуска. Если runner умеет выбрать
  только модуль, запусти модуль и укажи ограничение, не строй обходной runner.
- После PASS на финальном коде не повторяй тот же набор без причины. Второй прогон
  нужен при новой/изменённой подготовке или очистке, проверке повторного импорта,
  нестабильном результате либо требовании проекта; сохраняй отдельную цель повтора.
- Обязательные статические проверки проекта сохраняются. Не повторяй их на том
  же коде, не запускай MCP и CLI для подтверждения одного результата и не исправляй
  посторонний стиль ради проверки. Недоступный анализатор обозначь ограничением.
- После FAIL исправь подтверждённую причину и повтори затронутую проверку. Расширяй
  набор только при новом риске/влиянии. После обязательного smoke и проверок
  выбранного уровня завершай задачу; в отчёте укажи время и фактический набор.

## Проверка окружения до WORK

Для запроса только на план или ревью достаточно исследовать конфигурацию и исходники;
не запускай проверку сервисов, сборку или подготовку ИБ без необходимости для этого
запроса. До исполнения проверь обязательные для выбранного уровня возможности.

До изменения production-кода или написания тестов для уже готового кода проверь необходимые возможности:

1. `v8project.yaml` и, если есть, `v8project.local.yaml`, тестовую ИБ и доступность `v8_runner` MCP либо CLI; не выводи секреты локального профиля;
2. наличие тестового source-set YAxUnit для изменений BSL;
3. `tools.va.epf_path`, профиль `tests.va` и каталог feature для изменений UI/E2E; наличие Vanessa MCP зафиксируй как дополнительную диагностическую возможность, но не считай обязательным условием запуска.

Результат сообщи одним коротким блоком: `full`, `yaxunit_only` или `limited`. `yaxunit_only` допустим без паузы для задачи без UI; если UI/E2E входит в требования, создай Vanessa-сценарий. Если обязательный уровень технически недоступен, до WORK получи явное согласие пользователя на ограниченную проверку и сохрани это ограничение в артефактах задачи.

## MCP-first: как обращаться к v8-runner

Если в текущей сессии доступны инструменты MCP-сервера `v8_runner`, используй их вместо запуска эквивалентной CLI-команды через shell.

Ключевые операции:

- `run_module_tests` — основной цикл YAxUnit для конкретного модуля; передавай `moduleName` с **реальным** именем общего модуля. Этот вызов включает build prerequisite;
- `run_all_tests` — полный YAxUnit-прогон; для Vanessa используй `runner = "vanessa"` и параметры профиля/feature/tag только если они нужны;
- `build_project` — отдельная сборка, когда пользователь просит только build, при первичной диагностике или когда тест запускать ещё нельзя;
- `check_syntax_designer_modules`, `check_syntax_designer_config`, `check_syntax_edt` — применяй дополнительно по правилам `ai_rules_1c`, когда соответствующая проверка нужна;
- `dump_config`, `launch_app` — используй только по соответствующему назначению, не вместо test workflow.

Не делай двойную работу: после успешного `run_module_tests` не запускай тут же эквивалентный `v8-runner.exe test ...` только для подтверждения.

CLI нужен, когда:

- операция отсутствует в MCP, например `v8-runner.exe extensions --name <SourceSet>`;
- нужен намеренный `--no-build` — MCP `run_module_tests` работает в режиме BuildFirst;
- MCP `v8_runner` не доступен/не запустился;
- нужно проверить CLI help или диагностировать сам MCP-транспорт.

Подробно: [references/v8-runner.md](references/v8-runner.md).

## Выбор уровня тестирования

### YAxUnit — по умолчанию

Используй YAxUnit для общих модулей, модулей объекта/менеджера, расчётов, запросов, заполнения данных, проведения, движений, бизнес-правил, исключений и BSL-интеграций, которые можно проверить без пользовательского UI.

### Vanessa Automation

Используй Vanessa для форм, навигации, командного интерфейса, пользовательских прав, последовательностей действий пользователя и end-to-end бизнес-процессов.

Если изменение содержит и бизнес-логику, и пользовательский сценарий, используй оба уровня: YAxUnit для логики, Vanessa для критичного UI/E2E. Подробно: [references/vanessa.md](references/vanessa.md).

Для L4 достаточно одного подходящего smoke, проверяющего изменённый путь и его
результат; дублировать его в YAxUnit и Vanessa не требуется.

Перед созданием или изменением `.feature` **обязательно полностью прочитай** [references/vanessa.md](references/vanessa.md). Найди существующие шаги и подтверди элементы формы, выполни локальную проверку шагов и `scripts/check_vanessa_quality.py`, затем сразу запускай целевой сценарий через `v8_runner`. Vanessa MCP используй только если отчёт воспроизводимого запуска указывает на конкретную проблему шага или элемента, а логов и исходников недостаточно для диагностики. Не запускай сценарий целиком второй раз через Vanessa MCP «для отладки» и не продолжай его из неизвестного состояния TestClient.

Синтаксически корректный `.feature` не считается готовым тестом. Для PASS нужны содержательная проверка бизнес-результата, независимые управляемые данные, устойчивые локаторы, отсутствие необоснованных пауз и подтверждённый прогон с ненулевым числом выполненных сценариев.

## Перед изменением кода

Для вызова проверяемого API подтверди полный входной контракт: обязательные
параметры и ключи структур, типы и значения режимов. Отсутствующий ключ не считай
эквивалентом `Ложь` или значению по умолчанию без подтверждения в реализации.

1. Прочитай `USER-RULES.md`, `v8project.yaml` и существующую структуру `tests/`.
2. Определи функциональный блок изменения.
3. Найди существующий тестовый модуль, который владеет этой функциональностью.
4. Никогда не придумывай имя модуля для запуска. Имя должно существовать в `tests/src/CommonModules/` или фактическом source-set тестового расширения.
5. Если тестового модуля нет, создай его по [references/architecture.md](references/architecture.md).
6. Для исправления ошибки на L1–L3 по возможности сначала воспроизведи дефект тестом; на L4 достаточно smoke.
7. Перед первым тестовым вызовом проверь, доступен ли MCP `v8_runner`. Если доступен — используй `run_module_tests`; CLI не запускай без причины.
8. Если изменение затрагивает UI/E2E, найди существующий `.feature`; при его отсутствии создай новый по требованиям и [правилам Vanessa](references/vanessa.md).

## Функциональная архитектура

Стандарт имён тестовых модулей:

`Тест_<ФункциональныйБлок>_<ТипОбъекта>_<ИмяОбъекта>[_<ТипМодуля>]`

Примеры:

- `Тест_Склад_Док_ПеремещениеТоваров_МО`
- `Тест_Продажи_ОМ_Ценообразование`
- `Тест_ВЕТИС_ОМ_ГашениеВходящихВСД`
- `Тест_Доставка_Док_ПутевойЛист_МО`
- `Тест_НСИ_Спр_Номенклатура_ММ`

Не создавай отдельный общий модуль на каждую задачу. Если функциональный модуль уже существует — добавь тест туда.

Номер задачи хранится в имени регрессионного теста, если он реально известен: `ЕР12854_ВесРассчитываетсяПоУпаковкам`. Не выдумывай номер задачи.

Отдельный модуль `Тест_Регрессия_<Номер>` допустим только когда регрессия охватывает несколько несвязанных функциональных владельцев и невозможно выбрать один канонический модуль.

Полная схема: [references/architecture.md](references/architecture.md).

## Тестовые данные

В плане для **каждой новой или изменённой** зависимости, включая организацию, поставщика, склад и
настройки, укажи: ключ/роль и проверку пригодности; способ создания или загрузки
при отсутствии; существующий либо планируемый помощник; очистку/восстановление.
Фраза «проверить наличие» без ветки подготовки не закрывает предусловие.
Если способ ещё не подтверждён, назови конкретную проверку API/метаданных, после
которой он будет определён. Не заменяй этот пробел требованием ручного заполнения.

Используй минимальную воспроизводимую основу настроенного стенда и данные,
создаваемые каждым тестом. До генерации проверь необходимые справочники, настройки
и связи основы по заданным ключам/ролям. Всё, чего не хватает для выполнения теста,
создай или загрузи через проектные помощники: это касается и основы, и данных
сценария. Если готовой фабрики нет, реализуй переиспользуемую подготовку; отсутствие
данных не является блокером и не перекладывается на ручное заполнение пользователем.
Не создавай объекты, отсутствие или создание которых проверяет сам тест.

Повторяемое создание объектов и связанных документов выноси в модули-помощники
по подсистемам или операциям, сохраняя структуру проекта. Фиксированные пять модулей
не обязательны. Тест получает конкретные ссылки, выполняет проверяемое действие
и проверяет результат; очистка учитывает созданные и изменённые данные.

Сначала подтверди один минимальный путь подготовки, затем расширяй набор тестов.
CF перед каждым тестом не разворачивай. Полный контракт и примеры ТН/перемещений
и номенклатуры для УПД: [references/test-data.md](references/test-data.md).

## Структура YAxUnit-модуля

Каждый тестовый модуль:

- является общим модулем тестового расширения;
- содержит `Процедура ИсполняемыеСценарии() Экспорт`;
- регистрирует тесты через `ЮТТесты`;
- использует Arrange → Act → Assert;
- проверяет результат через `ЮТест.ОжидаетЧто(...)` и специализированные утверждения YAxUnit;
- не зависит от порядка выполнения других тестов.

Пример: [templates/TestModule.bsl](templates/TestModule.bsl). Правила: [references/yaxunit.md](references/yaxunit.md).

## Создание нового тестового модуля

1. Убедись, что подходящего существующего модуля нет.
2. Определи функциональный блок и объект-владелец.
3. Сформируй имя по стандарту.
4. Создай общий модуль в тестовом расширении через установленный механизм `1c-metadata-manage`, если он доступен.
5. Убедись, что модуль зарегистрирован в конфигурации тестового расширения.
6. Не делай тестовый общий модуль `Глобальный` или `ВызовСервера`: YAxUnit не считает такие общие модули тестовыми.
7. Добавь `ИсполняемыеСценарии()` и тестовые процедуры.
8. Проверь реальное имя каталога/метаданных перед запуском.

## Стандартный цикл разработки

### Новая функциональность

1. Определи ожидаемое поведение.
2. Найди/создай канонический тестовый модуль.
3. Выбери покрытие по L1/L2/L3/L4; переиспользуй готовые тесты, добавь только недостающие.
4. Реализуй изменение BSL.
5. Если доступен MCP `v8_runner`, вызови `run_module_tests` с `moduleName = <РеальноеИмяТестовогоМодуля>`.
6. Если MCP недоступен, fallback:

```powershell
v8-runner.exe test yaxunit module <РеальноеИмяТестовогоМодуля>
```

7. При FAIL проанализируй причину и артефакты прогона.
8. Исправь только подтверждённую причину FAIL.
9. Повтори тот же узкий тест тем же способом.
10. Выполни обязательный smoke и остальные проверки выбранного уровня L1/L2/L3/L4.
Если нужен весь YAxUnit-набор, используй MCP `run_all_tests`; CLI fallback:

```powershell
v8-runner.exe test yaxunit all
```

### Исправление дефекта

Выбери уровень по объёму и риску. Для L4 достаточно `FIX → SMOKE`;
отдельный регрессионный тест не обязателен. Для L1–L3 предпочтителен цикл
`RED → FIX → GREEN → REGRESSION` в пределах выбранного покрытия.

Не откатывай чужие незакоммиченные изменения ради RED-проверки. Если безопасно воспроизвести старое поведение нельзя — напиши регрессионный тест и зафиксируй, что RED-фаза не подтверждена.

Подробно: [references/regression-workflow.md](references/regression-workflow.md).

## v8-runner — обязательный оркестратор

Если проект настроен через `v8project.yaml`, используй `v8-runner` как основной вход для build/test, но выбирай транспорт по правилу MCP-first.

### MCP — предпочтительно

Конкретный YAxUnit-модуль:

`run_module_tests(moduleName = "<РеальноеИмяМодуля>")`

Все YAxUnit-тесты:

`run_all_tests(runner = "yaxunit")`

Vanessa:

`run_all_tests(runner = "vanessa", ...)`

### CLI — fallback

```powershell
v8-runner.exe test yaxunit module <Модуль>
v8-runner.exe test yaxunit all
```

`--no-build` используй только когда база уже специально подготовлена:

```powershell
v8-runner.exe test --no-build yaxunit module <Модуль>
```

Параметр `full = true` у `run_module_tests` расширяет отчёт, а не пересобирает проект.
Для необходимой полной пересборки используй `build_project(fullRebuild = true)`,
затем узкий тест. CLI fallback:

```powershell
v8-runner.exe build --full-rebuild
v8-runner.exe test yaxunit module <Модуль>
```

Перед редкой CLI-опцией проверь `v8-runner.exe test --help` или актуальный skill/документацию установленной версии. Подробно: [references/v8-runner.md](references/v8-runner.md).

## Диагностика неуспешного теста

Сначала классифицируй проблему:

1. **Build failed** — тесты ещё не запускались.
2. **Tests failed** — есть реальный failed/error testcase.
3. **`junit_empty` / `0 сценариев`** — обычно проблема обнаружения/фильтра тестов, а не business FAIL.
4. **Enterprise startup / timeout** — инфраструктура запуска.
5. **MCP transport/tool error** — сначала отдели ошибку транспорта от ошибки build/test; не меняй BSL-код из-за транспортной ошибки.

При `junit_empty` используй структурированные diagnostics/artifacts из результата MCP либо открой `runner.log` из указанного run directory. Проверь строку `Загрузка сценариев завершена`, реальное имя общего модуля, `ИсполняемыеСценарии() Экспорт`, свойства модуля и активность тестового расширения.

После первой загрузки тестового расширения при необходимости отключи безопасный режим и защиту от опасных действий. Эта операция не входит в текущую MCP-поверхность v8-runner, поэтому используй CLI:

```powershell
v8-runner.exe extensions --name <РеальноеИмяSourceSet>
```

Имя source-set бери из `v8project.yaml`, не угадывай.

Не называй `junit_empty` «падением теста», пока `runner.log`/MCP-отчёт не подтверждает выполнение хотя бы одного сценария.

## Definition of Done

Задача с изменением BSL завершена только когда:

- код реализует требуемое поведение;
- подходящий YAxUnit-тест переиспользован, создан или обновлён согласно выбранному уровню;
- подходящий Vanessa-сценарий переиспользован, создан или обновлён, если выбранное покрытие включает UI/E2E;
- Vanessa-сценарий прошёл проверку шагов, `scripts/check_vanessa_quality.py` и авторский checklist из `references/vanessa.md`;
- тест находится в правильном функциональном модуле;
- тестовые данные не создают скрытой зависимости от состояния базы;
- предупреждения runtime разобраны: если они указывают на непригодные данные
  или непроверенный бизнес-результат, исправь фикстуру/проверки и повтори тест;
- обязательный дымовой тест и целевые проверки выбранного уровня реально запущены на финальном состоянии;
- результат PASS либо ограничение/FAIL честно описан;
- регрессия соответствует выбранному уровню и области влияния изменения;
- в отчёте указано, чем выполнялась проверка: `v8_runner MCP` или `v8-runner CLI`, и какие тесты реально прошли.

Не заявляй PASS по коду возврата build. PASS тестов должен подтверждаться отчётом YAxUnit/Vanessa.
